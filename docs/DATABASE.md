# Database Design

PostgreSQL 16. All schema changes go through Alembic migrations — the
application never creates production tables at startup.

## Entity Overview

```
users ──< conversations ──< messages
   │             │
   │             └──< agent_runs
   └──< memories
checkpoints / checkpoint_writes        (LangGraph thread state)
documents / faqs                       (demo data for the Database Agent;
                                        application-managed, NOT in migrations)
```

### agent_runs
Operational audit of every graph node execution: `id`, `conversation_id` (FK
CASCADE), `message_id` (FK SET NULL), `agent`, `status` (success/error),
`intent`, `confidence`, `latency_ms`, `prompt_version` (content hash),
`error_type`, `created_at`. Indexed `(conversation_id, created_at)`.

### checkpoints / checkpoint_writes
LangGraph durable state: `thread_id` (= conversation id), `checkpoint_ns`,
`checkpoint_id`, `parent_checkpoint_id`, serde `type` + `blob` (BYTEA),
`metadata_blob`. Writes table stores pending writes per task. Deleted with the
conversation (`DELETE /v1/conversations/{id}` clears the thread).

## Roles & Privileges

| Role | Used by | Privileges |
|---|---|---|
| `orchestrator` | the API | full DML on app schema |
| `orchestrator_ro` | the AI Database Agent **only** | `SELECT` on public schema tables; `default_transaction_read_only=on` + `statement_timeout` forced per connection |

The read-only role is created by `scripts/create_readonly_role.sql` (or the
compose init script) and is idempotent. A security test asserts the role
cannot `UPDATE` (PostgreSQL enforces it even if application code regressed).

## Concurrency Control

`ConversationRepository.append_turn` runs inside one transaction:
`SELECT … FOR UPDATE` on the conversation row, verifies `version == expected`,
inserts both messages with `seq = message_count / +1`, bumps `version` and
`message_count`. A mismatch raises `ConflictError` (HTTP 409) — the durable
guarantee that keeps concurrent turns from interleaving (the Redis lock is an
optimization ahead of this).

## Migration Workflow

```bash
python -m alembic -c migrations/alembic.ini upgrade head          # apply all
python -m alembic -c migrations/alembic.ini downgrade -1          # roll back one
python -m alembic -c migrations/alembic.ini revision --autogenerate -m "…"  # new
```

Review autogenerated migrations before applying: the demo tables
(`documents`/`faqs`) are application-managed and must not be dropped by
schema migrations (the committed migration shows the pattern).

## Known Limitations

- Semantic memory similarity is computed in Python over a bounded per-user
  candidate set (≤500 rows). For large corpora, move to pgvector with an ANN
  index — the `SemanticMemoryStore` interface isolates this change.
- API keys use SHA-256 lookup hashes (appropriate for high-entropy random
  keys); if user-chosen passwords were ever introduced, use Argon2/bcrypt.
